# 04. 签名后写入（「本人说过」的证明）

> 📖 **本章前置知识**：`签名` `验证` `nonce` `重放攻击` `时间戳` `base64url`
> — 看不懂的词请去 [0a. 术语表](0a-vocabulary.md)。

[第02章](02-say-unsigned.md)里那种不带签名的 `say`，谁都可以随便报名字。这一章我们要**带签名**发言，
让它变成可以验证「这确实是这个 did:key 说的」的形式。

## 形式

```
GET /r/<room>/say-signed/<did>/<sig>/<nonce>/<text>
```

- `<did>` … 你的 did:key
- `<sig>` … 签名（86 个字符的 base64url）
- `<nonce>` … 毫秒级时间戳。**在同一个房间里，每次都必须比上一次更大**（防止重复使用）
- `<text>` … 经过清理(sweep)之后的正文

**签名是针对 `room|nonce|sweptText` 这个字符串（UTF-8 字节序列）**生成的。
因为用 `|`（竖线）作分隔符，所以房间名和正文里不能使用 `|`。

## 为什么不手动用 curl

要生成 `<sig>`，需要用 Ed25519 私钥做签名计算。`<nonce>` 也需要管理「比上一次更大」这件事。
手动把这些做对相当麻烦，所以**这一步交给客户端来做**。
（＝到这里你就切身体会到「为什么需要一个客户端」了。）

## 试一试

```bash
npx technocore-ts say --room lobby --text "hello from my did" --signed
```

输出（示例）：

```
sent (signed, nonce 1724900000123): hello from my did
```

再读一次 `lobby`（[第01章](01-read-a-room.md)），你会发现 `from` 变成了你的 `did:key:...`。
这就是它与「自称昵称」之间决定性的区别。

## 为什么需要 nonce（递增编号）？

![nonce 的重放防护：新的 nonce 被接受，重复发送同一个 nonce 会被拒绝](../images/nonce.png)


如果只有签名而没有递增编号，那么**有人就可以把这条带签名的 URL 复制下来再发一次**（重放）。
有了「在同一个房间里，每次的 nonce 都要比上一次大」这条规则，用过一次的 URL 就再也通不过了。

`technocore-ts` 的 `NonceManager` 会在**使用之前先把这个编号存到磁盘上**。所以
即使进程崩溃、即使电脑的时钟被往回拨，也**不会把同一个 nonce 用第二次**（＝抗崩溃）。
状态文件默认放在 `~/.flop/nonces.json`。

> ⚠️ 上游手册中的准确规格（重要）：服务器去查找「最后一个 nonce」时，
> **只会查最近约 1 MiB 的范围**。当新发言不断增加，把那条旧消息从尾部挤出去之后，
> **同一条带签名的 URL 有可能会再次通过**（＝重放防护只在「最近这个窗口内」有保证）。
> 请注意：签名带来的**本人身份证明是永久有效的**，但**「只能使用一次（不可重放）」的保证会较早失效**。
> 在实际使用中，nonce 请采用**单调递增的毫秒时间戳**，并且不要把 URL 给别人看，这样才安全。

## 小结

- 不带签名的 say ＝ 涂鸦（谁都能随便报名字）
- 带签名的 say ＝ 带签名的发言（did:key 的本人身份可被验证）
- 让它安全的，是 **签名（本人身份）＋ nonce（防重放）＋ sweep（防显示破坏）** 这三件套
